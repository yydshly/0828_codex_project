PDF STRUCTURING / RAG PREPROCESSING / 2026-08-29

NATIVE PDF,
STRUCTURED.

它不是新的 PDF 理论，也不是完整 RAG。它是一套面向数字原生技术手册的确定性结构恢复代码：把 PDF 对象整理成更可检索、可分块、可回溯的材料。

01

ESSENCE

它占据的是“读取 PDF”与“进入 RAG”之间的那一层。

PDF 底层更像绘图指令：在某个坐标写文字、画线、放图片。直接解析能拿到对象，却未必知道对象之间的文档关系。这个库的价值，是把对象重新组合成章节、表格、图、图题和阅读顺序。

ROUTE COMPARISON

三种处理路线，解决的问题不同

速度最快
输出文字与基础坐标
适合简单单栏 PDF

成本最低，但表格可能被摊平成文字，多栏顺序、图片关联和来源结构需要自己继续开发。

速度比模型路线快
输出MD + CSV + PNG + IR
适合长篇原生技术手册

利用原生文字和图元做确定性结构恢复；比直接提取多做大量几何判断，但避免整页 OCR、模型推理和网络调用。

速度通常更慢
输出结构 + OCR + 语义
适合扫描件与复杂视觉

可以识别扫描文字、公式和图片含义，覆盖面更大；代价是模型、算力、部署复杂度和可能的非确定性。

02

CAPABILITY

核心不是“识别所有细节”，而是尽可能恢复结构关系。

它覆盖对象提取与结构推断，不覆盖业务语义理解。规则支持过的版式会稳定复现，未覆盖的特殊版式仍然可能误判。

CAN DO已实现的结构能力
  • 原生文字保留字体、字号、方向和坐标
  • 阅读顺序多栏、旋转文字、编号窄列
  • 表格原生检测、几何补检、PNG/CSV 兜底
  • 复合视觉区位图、矢量、引线、标签合并
  • 内容归属表格、图片、正文之间的 Claim 仲裁
  • 来源追踪页码、bbox、图元 ID 和输出路径
CANNOT DO明确不解决的问题
  • 扫描识字没有 OCR，纯图片页无法恢复文字
  • 图片理解能保留设备图，但不知道设备图含义
  • 复杂公式语义默认截图，LaTeX 只做保守尝试
  • 全格式通吃艺术排版、表单、罕见结构仍可能失败
  • 完整 RAG不提供 Embedding、向量库和问答
  • 公开精度保证没有统一公开数据集对标结论
01

表格多路径兜底

原生检测失败时使用规则线几何补检；复杂表格宁愿保留 PNG，也不强行输出错误的 Markdown。

02

Claim 冲突仲裁

多个检测器争用同一文字或线条时，根据优先级、置信度和关键特征决定归属，减少重复。

03

双 bbox 设计

render_bbox 决定完整截图，sort_bbox 只承担排序锚点，避免大图破坏阅读顺序。

04

可审计输出

调试模式保留 IR、Claim、页面阶段、冲突和来源数据，便于定位规则为什么失效。

03

SCENARIOS

它的价值高度依赖语料类型。

不是“处理 PDF 就应该用它”，而是先判断文档是否数字原生、是否结构复杂、是否需要 RAG 和来源追踪。

Q1

文字可以直接选中吗？

否 → 先用 OCR、MinerU、Docling 或 Marker。

→
Q2

只是简单正文吗？

是 → 直接 PyMuPDF 通常更简单、更快。

→
Q3

是长篇技术手册吗？

是 → nativePDF 值得作为候选解析器测试。

HIGH FIT

设备与维修手册

数十到数百页，图、编号、引线、参数表和重复模板大量混排。

HIGH FIT

工业产品目录

需要同时保留参数 CSV、尺寸图 PNG、章节路径与具体页码。

HIGH FIT

离线 RAG 预处理

不希望上传私密文档，也不希望对每页运行 OCR/VLM。

MEDIUM FIT

混合解析前置层

原生页走规则结构化，只把扫描页和复杂图路由给模型。

LOW FIT

扫描档案

没有健康文字层，核心能力无法启动。

LOW FIT

公式论文与视觉问答

需要公式识别、图表语义或跨模态理解，应使用模型路线。

04

ALTERNATIVES

它不是空白市场；最接近的对照是 PyMuPDF4LLM。

选型不应比较宣传功能数量，而应使用自己的坏样本对照：文字覆盖、阅读顺序、表格完整性、视觉区整体性、重复率、来源追踪和每页成本。

产品技术路线优势更适合相对 nativePDF
nativePDF本次研究规则 + 几何
无 OCR / 模型		确定性、复合矢量区、Claim 与 provenance数字原生工业手册目标更窄，工程边界更专用
PyMuPDF4LLM ↗最接近基线原生提取 + 布局分析 + 按需 OCR成熟、轻量、Markdown/JSON、RAG 集成通用数字原生 PDF优先做 A/B，通常应先作为默认基线
Docling ↗完整框架布局模型 + 表格模型 + OCR丰富文档树、RAG Chunker、多格式企业通用文档流水线更重、更通用，结构模型更完整
MinerU ↗复杂文档OCR + 布局 + 公式 + VLM扫描件、公式、表格、多语言论文与复杂混合文档覆盖更广，但模型和部署成本更高
Marker ↗模型流水线深度模型 + OCR + 可选 LLM公式、复杂排版、多输出格式教材、论文、扫描件更强调模型精度，可使用 GPU
Unstructured ↗企业接入规则 / hi-res / OCR 多策略连接器、分块、多数据源摄取企业级 RAG ingestion平台能力更强，单类手册未必更精细
RECOMMENDED BENCHMARK 先比较 PyMuPDF4LLM，再比较一条模型路线。

若自有文档是 OEM 手册：选 10–20 份代表 PDF，每份挑 5–10 个最难页面，对照 nativePDF、PyMuPDF4LLM 和 MinerU/Docling。没有自己的坏样本，就无法判断这个专用库是否真的有额外价值。

05

EXTENSIONS

最有价值的扩展，不是继续堆规则，而是建立混合路由和质量闭环。

P0
HYBRID ROUTER

按页选择原生、OCR 或 VLM

检测文字层健康度；干净页面保留原生文字，扫描或乱码区域才调用模型，统一回写同一 IR。

P0
RAG CHUNKER

按章节和结构节点分块

让表格、图题、说明段保持原子性，并让块继承章节路径、页码、型号与来源坐标。

P1
DOMAIN PROFILES

厂商和模板 Profile

把页眉区域、字体层级、表格阈值和视觉合并规则变成可配置的 OEM 文档 Profile。

P1
SEMANTIC LINKS

图—编号—说明表关系图

在不改动原始 provenance 的前提下，用规则或 VLM 建立设备图与说明表的显式链接。

P2
EVALUATION

公开坏样本与下游 RAG 指标

补充真实 PDF 回归、元素级结构指标，以及最终问答准确率，而不只比较输出文件 hash。

P2
PRODUCTION

批处理、并行、缓存与服务化

增加失败队列、增量处理、对象存储和跨平台 CI，并处理 PyMuPDF 的商业许可边界。

06

OUR DECISION

暂不深挖通用理论；保留为专用能力与工程样本。

为什么不作为核心研究

规则、坐标、表格检测和阅读顺序都是成熟方向；项目的创新更多是针对特定手册的工程组合，而非新的文档理解范式。

为什么仍值得保留

Claim 所有权、双 bbox、复合矢量区域和 provenance 是不错的工程参考；在目标语料上也可能比通用模型更便宜、更稳定。

什么条件下重新启动

当我们拥有大量数字原生 OEM 手册，并发现 PyMuPDF4LLM 或现有解析器在设备图、表格关联和回溯方面持续失败时。

ADOPTION RULE 没有匹配语料，不投入；出现重复失败，再以真实坏样本启动 A/B。
