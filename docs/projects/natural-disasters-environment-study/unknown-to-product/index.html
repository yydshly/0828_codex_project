NOW · CASE 001当下目标

从零解释并复现海洋极端天气效果

以固定提交的真实演示为目标，回答效果由哪些视觉层组成、每层依据什么资料、最小实现顺序是什么，以及做到什么程度才算通过。

  • 目标画面可观察、可拆解
  • 论文、源码和运行证据可追溯

01 / UNIVERSAL LOOP

陌生领域探索，不从“我要学什么”开始。

从一个可观察的目标结果开始，然后逐步收窄未知。流程的每一步都必须产生一个以后可复用的工程资产。

  1. 01目标锁定OUTCOME

    固定参考画面、交互或输出，写清观众必须看到什么。

    产出：Target Brief
  2. 02来源考古PROVENANCE

    找到论文、官方演讲、权威实现、固定源码和许可证。

    产出：Source Ledger
  3. 03效果反推DECOMPOSE

    把视觉结果拆成可控制层，并映射到算法和代码模块。

    产出：Effect Map
  4. 04最小复现PROTOTYPE

    每次只证明一个关键机制，不先堆完整场景。

    产出：Bounded Demo
  5. 05证据验收VALIDATE

    固定镜头、参数、设备和指标，与目标逐层比较。

    产出：Scorecard
  6. 06能力抽取CONTRACT

    将一次性实现抽成生命周期、参数协议和调试接口。

    产出：Adapter
  7. 07真实用例PRODUCT

    接入游戏、IP 或素材生产，验证它是否解决真实问题。

    产出：Vertical Slice
  8. 08方法回收TRANSFER

    只把有运行证据、能跨案例复用的部分写入母方法。

    产出：Pattern Update
继续

证据更接近目标，且下一步成本可控。

转向

目标有效，但当前算法或实现路线不匹配。

停止

连续 2–3 轮没有新增证据，或需要超出范围的新架构。

02 / EVIDENCE SYSTEM

资料不是一堆链接，而是一条可审计证据链。

论文说明方法从哪里来；源码说明作者如何实现；目标媒体说明想达到什么；运行证据说明我们实际证明了什么。四者不能混用。

PRIMARY_SOURCE

原始论文与官方演讲

回答算法提出者、假设、公式、限制和评估方法。

不能单独证明当前仓库实现正确。
UPSTREAM_SOURCE

固定提交源码

回答当前版本实际用了哪些模块、参数、Pass 和近似。

不能单独证明浏览器能够稳定运行。
TARGET_MEDIA

官方目标画面

回答视觉层次、构图、尺度、光照和状态差异。

不能当作本地复现截图。
RUNTIME_EVIDENCE

真实运行记录

回答某个固定环境中功能、状态、错误和性能观察。

不能外推到未测试设备和科学准确性。
OUR_METHOD

我们的分析方法

把来源、画面、源码与实验组织成可执行流程。

必须标明哪些结论仍是推断。
PLANNED

待实现产品能力

描述版本、接口、门禁和资源预算。

规划不是已经具备的功能。

03 / CASE 001 · NATURAL DISASTERS

先解释画面为什么成立，再解释代码在哪里。

观众看到的是一场风暴；实现上它是六个相互影响的渲染与编排系统。任意一层缺失，画面都会从“环境”退化成“单一特效”。

TARGET_MEDIA 图片来自固定上游提交，只用于分析视觉目标；它们不是我们的复现结果或本地性能证据。

01
ATMOSPHERE

天空、大气透视与太阳

Rayleigh / Mie 散射与 LUT 提供天空颜色、太阳透射和远景雾化，让海洋与云使用同一套光照语境。

源码
Atmosphere.js / AtmosphereGLSL.js
原理
Bruneton / Hillaire style LUT
验收
固定镜头改变太阳高度，地平线仍有层次
02
CLOUD VOLUME

可穿透、有明暗的云体

3D Perlin-Worley 密度与 2D 天气图定义云形，通过 ray marching 积分密度和光照，再用时域重投影降低成本。

源码
ProceduralTextures.js / Clouds.js
原理
density field + light march + reprojection
验收
云顶明、云底暗，近云与远云尺度可辨
03
OCEAN FIELD

多尺度浪、浪尖与白沫

三层 JONSWAP 波谱分别覆盖涌浪、风浪和细浪；GPU butterfly IFFT 生成位移与导数，Jacobian 和陡峭度驱动泡沫历史。

源码
OceanFFT.js / OceanMesh.js
原理
spectrum → time evolution → IFFT
验收
前景、中景和地平线保留不同频段
04
WEATHER & EVENTS

连续天气与电影化灾害场

Weather 插值统一风、云、雨、雾和海况；海啸、疯狗浪和涡旋使用解析高度场，不是 CFD 或真实灾害预测。

源码
Weather.js / Director.js / Waterspout.js
原理

验收

05

04 / RESOURCE ACQUISITION

从零获取的，不只是代码。

一个高质量复现至少需要八类资源。缺少其中任何一类，都要在计划里显式标记，而不是让大模型或开发者自行猜测。

01

目标参考

官方截图、视频、固定镜头、不同状态和动态节奏。

判断“要做到什么”
02

原始理论

论文、作者演讲、课程资料、公式和假设。

判断“为什么成立”
03

权威实现

作者代码、官方示例、测试和已知限制。

判断“如何正确实现”
04

目标源码

固定 commit、依赖、模块图、Shader 与构建脚本。

判断“仓库实际做了什么”
05

运行环境

浏览器、GPU、扩展、分辨率、质量档和设备限制。

判断“在哪里能运行”
06

测试证据

固定参数、截图、状态采样、帧时间与错误日志。

判断“我们证明了什么”
07

许可与归属

代码许可证、媒体归属、模型/纹理来源和商用边界。

判断“能否继续使用”
08

产品约束

用户、使用场景、加载预算、输出格式和维护成本。

判断“是否值得产品化”
采集顺序如何避免一开始就陷入海量资料？
  1. 先选 3–5 张能够代表状态差异的目标图，不先收集整套论文。
  2. 根据画面写出“必须看到”的观察项，再查每一项背后的关键词。
  3. 优先找作者/官方来源，然后找对应的可运行实现。
  4. 把每个来源绑定到一个具体问题；无法回答问题的链接不进入核心资料包。
  5. 固定版本、保存许可和引用信息，避免后期无法复现。

05 / FROM ZERO ROADMAP

从空目录到优秀效果，分十二步实现。

顺序的核心是先建立可观测性，再逐层增加物理和视觉复杂度。每个阶段都能独立失败、回退或停止。

交付

门禁

06 / VALIDATION SYSTEM

优秀效果不是“感觉不错”，而是一组可重复证据。

视觉验收、数学诊断、运行正确性和产品可用性需要分别记录。通过一个层级，不能替代另一个层级。

  • 同机位截图
  • 盲读状态
B

算法诊断

频谱、位移、导数、密度、首次命中和时域历史是否处于预期范围。

  • 中间纹理
  • 统计区间
  • CPU/GPU 对照
C

运行证据

启动、状态切换、重播、复位、错误处理和资源释放是否可观察。

  • Console
  • 状态采样
  • 自动浏览器路径
D

性能预算

在命名设备、固定分辨率和质量档下记录 CPU/GPU 时间与资产成本。

  • 帧时间分解
  • 显存/资源
  • 质量档变化
E

产品门禁

第二个宿主能否通过协议使用能力，并在用户任务中产生可衡量价值。

  • 接入成本
  • 可控性
  • 维护与许可

若仍无新增证据，停止自动修复并输出阻塞报告。

报告内容

现象、已验证项、失败尝试、最可能根因、需要的新输入或决策。

07 / MODEL-ASSISTED EXPLORATION

大模型负责翻译和编排，运行时负责确定性。

最稳妥的产品形态不是每次让模型重新写 Shader，而是让模型使用经过验证的资料和协议，生成实现任务或结构化场景。

MODE A · RESEARCH / BUILD

模型生成与修复渲染代码

用于研究新算法：检索相关资料，解释公式，生成一个模块，运行浏览器，读取截图/日志，再进行有限修复。

  1. 只提供相关论文段落和源码
  2. 限定一个 Pass 或模块
  3. 声明输入、输出和 GPU 资源
  4. 附带固定镜头和验收指标
  5. 最多 2–3 轮自动修复
适合：探索未知能力
MODE B · PRODUCT / GENERATE

模型生成场景协议

用于稳定生产：把自然语言转为 WeatherSpec、EventSpec 和 ShotSpec，再交给确定性运行时执行、预览与导出。

  1. 自然语言描述目标氛围
  2. 模型输出受 Schema 约束的 JSON
  3. 运行时校验并应用参数
  4. 浏览器返回截图与性能
  5. 模型只调整允许的字段
适合：游戏、IP、素材批量生产
