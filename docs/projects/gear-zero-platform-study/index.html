01 / CORE JUDGMENT

不把它当技术教材，
把它当产品能力地图。

Gear Zero 网页没有公开足够的内部实现，无法直接回答它使用了哪些模型、游戏引擎、Skill 协议或调度策略；但它清楚展示了一套值得复用的产品承诺。

一个能力成为产品＝ Skills ＋ 结构化状态 ＋ 工作流调度 ＋ 自动验证 ＋ 可体验成果 ＋ 持续迭代 ＋ 发布分发。

公开可确认

它向用户交付什么

通过对话规划和构建游戏，在构建期间继续收集想法，将每轮需求变成可玩的版本，并支持共同创作。

可以合理推断

它需要哪些系统

结构化项目状态、异步构建队列、专业能力调度、隔离执行、版本快照和可访问的预览发布。

我们的决策

应该参考什么

参考能力合同、用户旅程和产品闭环；不复制页面外壳，也不把未公开的内部技术当成事实。

为什么仍然具有研究价值？展开证据边界

它的底层技术研究价值目前有限，因为系统是黑盒；但它可以作为黑盒基准，帮助我们设计同一批需求，比较首个可玩版本时间、连续修改回归率、移动端表现、源码可维护性、成本和平台锁定。

Alaya Lab 公开的世界模型、生成式渲染和长程游戏智能体研究，说明其长期技术方向，但不能据此断言这些研究已经用于 Gear Zero 当前产品。

02 / CONVERSATION TRACE

我们的判断是怎样一步步形成的？

这次交流不是简单的竞品总结，而是四次连续抽象：从“它有什么”，走到“我们应该怎样构建下一类产品”。

  1. USER / 01

    这个网站的能力、原理、场景和意义是什么？

    从工具定位产品

    它的价值不只在生成代码，而在把模糊创意快速变成可玩的版本，并允许用户在试玩中继续塑造产品。

  2. USER / 02

    底层实际是 Skill，还是工作流调度？

    从单项能力定位系统

    答案不是二选一：Skill 是专业能力，Workflow 是生命周期，Orchestrator 负责动态决策，Project Brain 保持事实，Sandbox 与 Verifier 负责交付证据。

  3. USER / 03

    它对我们的研究意义是什么？

    从竞品定位研究问题

    研究重点由“如何做好一个 Skill”升级为“如何让多个 Skills 在长期项目中可靠协作，并通过可玩反馈持续演化”。

  4. USER / 04

    网页、游戏能力还能扩展到什么？

    从游戏定位通用平台

    凡是能被拆解、执行、验证、版本化和预览的数字能力，都可以形成一个由用户意图驱动的垂直 Studio。

03 / SYSTEM MODEL

它不是一个 Skill，
而是一条受约束的生产系统。

01USER INTENT用户表达目标、约束与判断

用户承担产品负责人角色，不需要先学会专业工具。

↓
02SPEC COMPILER把对话编译成结构化规格

主动追问、解决歧义，并形成可比较的需求差异。

↓
03ORCHESTRATOR规划任务、依赖、并行与恢复

根据项目状态选择 Skill，而不是执行固定提示词序列。

↓
04SKILL GRAPH调用领域内专业执行单元

每个 Skill 都有输入、输出、作用域、验收与回退合同。

↓
05BUILD + VERIFY生成真实成果并运行检查

隔离执行、自动试玩、错误诊断和回归验证提供事实。

↓
06VERSION + DISTRIBUTION形成版本、Fork 与传播

可体验成果成为下一轮沟通、协作与创作的共同对象。

外部表现能力抽象我们的实现验证问题

给出制作方案规划与确认Planner + Gate何时应由用户确认？

连续迭代增量开发Spec Diff + Tests如何防止修改破坏旧功能？
浏览器试玩可执行交付Sandbox + Preview完成是否有运行证据？
分享与 Fork分支与分发Version Graph创意能否持续二次演化？

04 / RESEARCH VALUE

它帮助我们把研究问题放到了正确层级。

H1

创意编译

结构化 GameSpec 是否比直接生成代码更能降低首版偏差？

H2

能力合同

统一 Skill Contract 是否能减少跨模块冲突和不可控修改？

H3

长期状态

项目记忆是否比不断增长的完整聊天上下文更稳定、更便宜？

H4

自动验证

编译、浏览器检查和自动试玩能否显著降低连续迭代回归率？

建议的消融实验

  1. BASE通用代码 Agent
  2. ＋S加入游戏 Skills
  3. ＋O加入 Orchestrator
  4. ＋M加入项目记忆
  5. ＋V加入自动试玩与验证

比较首个可玩版本时间、需求实现率、第五轮回归率、移动端表现、代码可维护性和每个有效版本成本。

06 / DOMAIN EXPANSION

同一个公共底座，
可以承载多个垂直 Studio。

不是用一个万能 Agent 生成所有东西，而是复用项目状态、调度、版本、权限和发布，再为每个领域建设独立的 Spec、Skills、运行时与验证器。

SHARED CORE Project Brain · Orchestrator · Sandbox · Verification · Versioning · Publishing
WEB PACK

AI Web Studio

网站、后台、数据库、部署与转化验证。

GAME PACK

AI Game Studio

玩法、关卡、战斗、资产、试玩与性能。

APP PACK

AI App Studio

移动界面、数据、通知、支付与发布。

CONTENT PACK

AI Content Studio

脚本、分镜、素材、剪辑与渠道版本。

OPS PACK

AI Operations Studio

业务流程、系统连接、异常处理与监控。

AGENT PACK

AI Agent Studio

职责、工具、记忆、定时执行与质量门。

扩展原则

新增领域不是增加几条 Prompt，而是增加一个完整 Domain Pack。只有当一种成果能够被结构化、执行、验证、版本化和预览时，才适合进入平台。

07 / RECOMMENDATIONS

类似项目应该怎样开始？

现在 · 收敛协议

先定义系统共同语言

  • 建立只覆盖一种游戏的 GameSpec v0.1
  • 统一五个核心 Skill Contract
  • 明确每个 Skill 的作用域、证据与回退
下一步 · 跑通闭环

从创意稳定走到 V2

  • 实现 Discover → Build → Verify 状态机
  • 固定一个 Three.js 动作游戏模板
  • 验证修改后旧功能仍然成立
以后 · 再做平台

等可靠性成立再扩展网络

  • 增加多人房间、Fork 和作品分发
  • 抽取 Web Pack 与 Game Pack 公共底座
  • 用真实项目数据决定商业化和生态
DO先做垂直、可验证、可导出的 Studio

范围越可控，越容易建立连续迭代的可靠性和真正的差异化。

DON'T一开始承诺“生成任何数字产品”

横向平台会掩盖每个领域缺失的规格、专业能力、运行时和验收方法。

08 / SOURCES & BOUNDARIES

我们知道什么，
还不知道什么？

KNOWN

官方确认 Gear Zero 面向对话式游戏规划、构建、持续想法收集和共同创作。

INFERRED

项目状态、异步队列、版本和隔离构建是根据外部行为推断出的必要机制，不代表其官方实现。

UNKNOWN

内部模型组合、具体游戏引擎、源码导出、商业权利、数据保留和私有部署方案仍缺少完整公开材料。
