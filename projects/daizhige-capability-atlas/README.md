## 结项摘要

本项目当前不继续投入研究。结论可以压缩为四句话：

1. 「殆知阁」是一套门类广、体量大的古籍纯文本集合，但不是全面、权威或版本完备的古籍总库。
2. 上游仓库可以作为**外部资料备份源和候选语料源**；本项目只保存目录审计、代表路径和判断依据，没有下载或镜像正文。
3. 它只有在古籍相关产品进入真实需求范围时才产生直接价值，例如全文检索、引用型问答、古籍阅读、历史研究或文化内容生产。
4. 在没有相关产品需求时，不值得继续投入下载、清洗、索引、校勘或知识图谱建设；保留这份档案即可降低未来重新调研的成本。

重新启用必须同时满足三个条件：存在明确的古籍产品需求；现有更权威或更易授权的数据源不能独立满足需求；团队愿意承担逐书核验、版本治理和许可确认成本。

## 核心判断

「殆知阁」原仓库是一套**大规模古籍纯文本集合**，不是一个已经完成的搜索产品、知识库或 AI 模型。对我们而言，它当前最合适的角色不是研发对象，而是**已登记的候选资料备份源**。

它最可靠的原生能力是：

```text
大规模纯文本汇集
→ 传统门类目录组织
→ 书名与正文的字面查找
→ Git 下载、镜像和版本固定
→ 脚本可批量处理的语料输入
```

全文搜索、语义问答、知识图谱、古今翻译和研究工作台都可以建立在它之上，但这些属于**被真实产品需求触发后的增强能力**，不能倒写成原仓库已经具备的能力，也不是当前计划。

## 能力分层

### 原仓库直接提供

1. **语料汇集与离线保存**：纯文本体积远小于扫描图，可完整镜像和批量处理。
2. **目录浏览**：用十大门类和子目录表达粗粒度主题分类。
3. **标题发现**：文件名承担书名或版本名称，可通过文件查找定位。
4. **字面检索**：GitHub 或本地文本工具可以查找人物、地名、术语和原句。
5. **可编程输入**：TXT 可以被 Python、Node、命令行和数据管线直接读取。
6. **版本固定**：Git commit 与 blob SHA 可作为可复现研究的输入边界。

### 维护版新增

`daizhige-org/daizhigev20` 已把数据和工具分支分开，并逐步增加 Markdown、YAML frontmatter、按卷拆分、来源链接、文本修正、Elasticsearch 导入脚本与 Web 搜索界面。维护版因此更接近“可持续整理的数据产品”，但仍需逐书判断来源、校勘与权利状态。

### 可以扩展，但原仓库没有

- 繁简、异体字、通假字归一后的精确检索；
- Elasticsearch 全文索引、高亮、布尔过滤与统计聚合；
- 关键词与向量结合的混合检索；
- 带书名、卷次、原文证据和来源链接的 RAG；
- 人物、地点、官职、年代、著作实体抽取与知识图谱；
- 版本对照、扫描页对齐、校勘注记与协作纠错；
- 古文断句、标点、翻译、OCR 纠错和评测数据集。

## 工作原理

原始架构可以概括为“文件系统即数据库”：

```text
目录路径 = 门类与子类
文件名   = 书名或版本名
TXT 正文 = 可检索文本
Git      = 分发、快照与变更历史
```

当它被升级为搜索产品时，导入程序读取路径和正文，抽取书名、门类等字段，再由 Elasticsearch 建立“词或字 → 文档与位置”的倒排索引。语义问答还需要章节切分、向量索引、重排、引用组装和回答约束。

## 使用场景

### 适合

- **原句与出处初查**：定位词语、人物、地名、药名、典故和固定表达出现在哪些文本中。
- **数字人文分析**：做词频、共现、文本相似度、概念流变和跨门类比较。
- **古汉语 NLP**：构造断句、标点、实体识别、翻译、语言模型继续训练或 OCR 纠错语料。
- **教学与阅读产品**：建设专题选本、课程例句、章节阅读和注释工作台。
- **文化内容创作**：为历史选题、游戏世界观、传统技艺和文学创作提供线索库。
- **数据产品研究**：验证如何把低结构语料升级为有来源、有版本、有检索证据的知识系统。

### 不适合直接承担

- 作为未经核对的权威点校本或唯一学术引文来源；
- 作为中医诊疗、处方或其他高风险决策依据；
- 未清洗就直接训练模型并假设文本可靠；
- 不核查许可、录入来源和点校权利就商业再分发；
- 直接把整书切成固定长度向量块后期待稳定、可引用的问答。

## 对本研究库的意义

Project 004 的当前价值不是立即建设古籍产品，而是把一个潜在外部资料源调查清楚、登记在册，并形成明确的启用边界。

> **现在归档，相关产品出现时再启用；避免重复调研，也避免为暂时不存在的需求提前建设。**

它为我们保留四类条件性价值：

- **资料源备忘**：已经知道仓库在哪里、规模多大、有哪些门类、主要风险是什么。
- **需求触发器**：只有古籍检索、阅读、研究、文化创作或古汉语 AI 进入产品范围时才重新打开。
- **评估基线**：未来可以用 commit、tree、路径和 hash 固定输入，并与 CText、CBETA、维基文库、机构数据库等来源比较。
- **决策节省**：明确当前不下载、不建索引、不做模型训练，避免没有业务闭环的前置投入。

当前投入决策：**研究闭合、资料归档、停止扩展。** 条件价值高于即时价值。

## 如被产品需求触发，建议扩展路线

以下不是当前计划，只是重新启用后的执行顺序：

1. **P0 · 可信数据层**：来源、版本、作者朝代、权利、hash、异常检测和质量等级。
2. **P1 · 稳定结构层**：书—卷—篇—章—段 ID，Markdown/TEI/JSONL，多版本映射。
3. **P2 · 可验证检索层**：逐字、异体归一、关键词、语义、重排和可复现查询。
4. **P3 · 证据型知识层**：原文、卷次、底本与来源同行展示；回答和推断明确区分。
5. **P4 · 研究工作台**：版本对比、批注、人物地理时间网络、专题数据导出和协作校勘。

如果未来重新启用，最合理的 MVP 不是处理全库，而是选 20–50 部来源较清楚的典籍，验证一条完整闭环：

```text
Corpus Manifest
→ 结构化切分
→ 混合检索
→ 引用型回答
→ 人工核验
→ 可量化评测
```

## 关键边界

- 本项目没有保存上游正文副本；“资料备份库”指已登记的外部候选资料源，不代表我们拥有可直接调用的本地镜像。
- 原始文本主要来自早期互联网汇集，作者、版本、底本、录入者和转换过程并不完整。
- 维护团队已记录机械繁简转换、论坛残留、HTML、脚本、乱码等问题，并在持续修订重点文本。
- 原仓库和当前维护 fork 均未检测到明确的仓库级 `LICENSE`。古籍原作进入公有领域，不自动解决现代录入、点校、注释、汇编和上游来源的全部权利问题。
- 本项目描述的是仓库结构和可支持的能力，不评价每一部书的文本可靠性。

## 归档决定

- 当前状态：`已归档`。
- 当前动作：保留总结、审计快照和在线页面，不继续研究或处理正文。
- 重新启用触发：出现明确的古籍相关产品、研究任务或内容生产需求。
- 重新启用第一步：先比较更权威、更完整或授权更清楚的替代资料源，再决定是否使用殆知阁。
